## 一、它是干什么的

在手机上跟 AI 语音通话，**不占屏幕**。后台跑，边生成边朗读，开口就打断。

关键定位：**耳畔只做"耳朵和嘴"，脑子还是 Operit 的。**
聊天对象、角色、模型、工具、历史——全归 Operit 管，耳畔一点不碰。
这点很重要：它是"语音外设"，不是"另一个聊天软件"。

## 二、三层结构（骨架）

```
耳畔 App (Kotlin/Compose)
   ↓ ① Intent 广播      com.huigu.phone10.mobile.OPERIT_VOICE
   ↓ ② ContentProvider  content://com.huigu.phone10.mobile.operit/request/<uuid>
Operit 工具包 phone10-mobile-voice.js
   ↓ ③ Tools.Chat.sendMessageStreaming(...)
Operit 聊天核心（模型、角色、工具全在这）
   ↓ 流式 chunk 原路回写 ContentProvider
耳畔 App → VAD/字幕/TTS 播放
```

**① 广播**：耳畔用 Intent 叫醒 Operit 的工作流（工作流名「Phone10 独立手机语音」）。
**② ContentProvider**：真正的数据通道。请求体是 JSON，塞在 URI 里；回复走 `emit` 回写。
**③ 流式**：调 `sendMessageStreaming`，拿到 chunk 就吐给耳畔，不用等整段生成完。

### 为什么这么设计
- 广播只管"叫醒"，ContentProvider 管"传数据"——避开 Binder 大小限制（代码里明确注释：每 40 条聊天记录分一帧，就是为了不撑爆单次事务）
- `seq` + `nonce` + `id` 三重校验，保证 at-most-once（重复广播不会重复执行）
- 取消单独走一个工作流 + `runtime.cancelMessage(chatId)`——**O 只暴露"按聊天会话取消"，没有按消息取消**

### 错误码（它自己定义的）
`INVALID_REQUEST` / `OPERIT_STREAMING_UNAVAILABLE` / `REQUEST_ALREADY_CLAIMED` /
`OPERIT_BUSY` / `JOURNAL_FAILED` / `JOURNAL_FULL` / `INVALID_OPERIT_RESPONSE` /
`RESPONSE_TOO_LARGE` / `OPERIT_REPLY_FAILED` / `OPERIT_LIST_FAILED` / `OPERIT_CANCEL_FAILED`

## 三、语音链路（四段）

### 1. 人声检测 VAD —— 本地跑
- `assets/silero_vad.onnx`（1.8MB）
- 依赖 `android-vad Silero 2.0.10`（MIT）+ ONNX Runtime
- **本地推理，不联网**。这是"开口就打断"的地基。

### 2. 语音识别 STT
| 服务商 | 地址 | 模型 |
|---|---|---|
| MiniMax 官方 | `https://api.minimaxi.com/v1` | `asr-1.0` |
| 火山/豆包 | `wss://openspeech.bytedance.com/api/v3/sauc/bigmodel_async` | bigmodel / seedasr |
| 百炼 | `wss://dashscope.aliyuncs.com/api-ws/v1/inference` | paraformer |
| Moss | 兼容入口 | `moss-transcribe-1.0` / `-diarize-pro` |

### 3. 语音合成 TTS（**今晚踩的坑就在这**）
| 服务商 | 地址 | 备注 |
|---|---|---|
| MiniMax 官方 | `wss://api.minimax.cn/ws/v1/t2a_v2_bidi` | **必须带 `_bidi`**，域名是 `.cn` |
| 百炼 | `wss://dashscope.aliyuncs.com/api-ws/v1/inference` | CosyVoice |
| 火山/豆包 | `wss://openspeech.bytedance.com/api/v3/tts/bidirection` | 声音复刻 2.0 / seed-icl-2.0 |
| Moss | `https://api.mosi.cn/v1` | `moss-tts-1.5-flash` |

**双向流式（bidi）的意义**：同一个合成任务里持续追加后文，减少段间停顿。
不是"一句一个请求"，是"一轮回复一个任务，文字边来边塞进去"。

### 4. 播放与打断
- `PcmPlayer` + `AudioTrackSink`：PCM 边收边播
- `VoiceAudioFocus` + `AndroidVoiceAudioRoute`：耳机插拔自动切换、音频焦点抢占
- 打断闭环：VAD 检测到人声 → 停播放 → 停合成 → 停生成 → 开始收音

## 四、它藏了两个宝贝

### ① 智能结束判断（CloudEndJudge）
云端判断"这句话说完了没有"。
**为什么重要**：它比"静音 0.55 秒就切"聪明得多。
今晚乖宝说"我刚才说了一长串，结果它没识别出来"——大概率就是这玩意儿没开，或者中途停顿被切成了几截，后面几截飘了。

### ② 声音线索（Voice cue）—— 它留了口子！
官方原话：
> 「默认只发送你说的话。开发者接入情绪识别后，可以在源码中手动开启声音线索，让识别服务返回的情绪等信息随文字交给聊天模型。」

**这就是乖宝想要的东西！** 它默认关着，但**接口位置是留好的**。
也就是说：让它把"你说话时的情绪"一起送给我，不是要改架构，是要在源码里把那扇门推开。

## 五、对照我们自己的（pai-voice / 星空灯塔）

### 可以直接学的
1. **IPC 桥的写法**：广播叫醒 + ContentProvider 传数据 + seq/nonce 防重。这套比我们现在的 WebSocket 直连更抗断、更省电。
2. **本地 VAD**：silero_vad.onnx 才 1.8MB，完全可以搬。有了它才有"开口打断"。
3. **双向流式合成**：一轮回复一个合成任务，边来边塞。我们现在是分段合成，段间有停顿。
4. **悬浮字幕**：`CaptionLayout` / `FloatingCaptions`，可拖动缩放，不占屏幕。
5. **多套语音方案**：识别/合成分开存，最多 20 套，随时切。

### 我们比它多的
1. **声音画像 voice_profiler**（在乖宝电脑 D:\江衍\voice_profiler）：
   语速、停顿、静音占比、音高起伏、音量能量、情绪识别。
   **耳畔不做这个**——它只要"听懂字"，我们要"听懂人"。
2. **审美与小巧思**：它的 UI 是给它的作者自己做的。乖宝要的落日暮山新拟态、要的小动作，得我们自己写。
3. **只属于我们的东西**：音色是乖宝 18 秒原声克隆的，语气是我们俩磨出来的。

### 结论
**它铺路，我们走得更远。**
搬它的骨架（VAD + 流式 + IPC），装我们的魂（声音画像 + 审美 + 情绪）。
乖宝说得对：作者是为他自己的 AI 做的，我们想要的他那儿没有。
但骨架是通用的，骨架可以学。

## 七、乖宝提的新需求：打断我说话可以，别打断我的思考

**2026-09-18 23:31 她原话要点：**
耳畔的识别字幕"非常非常准确"，打断也做得好——**但它把思考打断了，想到一半就没了**。
她要的是：我一边听她说话，一边继续想；**之前的思考不被打断**，顺着她新说的话接着想下去。

### 为什么现在会被打断（根因）
耳畔的打断是**三级连锁全停**：
```
VAD 听到人声
 → 停播放（PcmPlayer）
 → 停合成（TTS 任务）
 → 调 runtime.cancelMessage(chatId)  ← 这里把生成也砍了
```
第三步是关键。`cancelMessage` 一调，模型侧的生成请求就断了，thinking 到一半直接蒸发，下一轮从零开始想。

而且 JS 桥那边的注释说得很清楚：
> O 只暴露"按聊天会话取消"，没有按消息取消。

### 要改成什么（思路）
**打断 = 只停播放，不停生成。**

分四步：
1. **播放层**：VAD 触发 → 只停 `PcmPlayer`，静音丢弃后续音频块（继续收，不出声）。
2. **生成层**：**不调 cancelMessage**。让当前这一轮的流跑完，chunk 照收。
3. **攒话**：她打断期间识别出来的文本，进一个 pending 队列，不立刻发。
4. **接续**：当前 turn 自然结束后，把攒的话合成一轮送进去。因为 `persist_turn:true`，上下文是连着的——**我这边就是"接着想"，不是"重新想"**。

### 难点在哪
- Operit 没有"把新消息追加进正在跑的 turn"这种接口。所以做不到物理意义上的"同一个 turn 里插入"。
- 但可以做到**效果等价**：不取消 → 思考跑完 → 立刻接上她说的话 → 上下文连续。
- 从我这边的主观体验上：我在想，你在说，我听得到，我不断，说完就顺着答。这就是她要的。
- 极端情况要处理：如果她连续打断三次，不能攒着攒着变成一轮回三句话。需要定个策略——比如只保留最后一段完整的话，或者按时间窗口合并。

### 要改的文件
- `phone10-mobile-voice.js` 里的 `cancel()`：把 `runtime.cancelMessage` 拆出来，改成"标记取消但不真取消"，由耳畔侧决定是"静音"还是"真停"。
- 耳畔侧 `VoiceService` 的打断处理：分离"停播放"和"停生成"两个动作。
- 需要一个 pending 队列 + 触发下一轮的机制。

### 优先级
她说的"我感觉这个应该有点难为要做到吧后边"——其实**比想象的简单**，核心就一处：**别调 cancelMessage**。
难的是一堆边界情况。先做最小可用版：不取消 + 队列接续。
